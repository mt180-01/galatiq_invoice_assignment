# Extraction on invoices written by someone else

Generated by `python scripts/evaluate_extraction.py`; do not edit by hand. **58 invoices** in twelve styles (aligned columns, email prose, one-cell-per-line PDF text, OCR-damaged, terse purchase-order, multi-line descriptions, near-miss reference numbers, bullets, two-column layouts, quoted email threads, ALL CAPS, formal letters).

**Why this set.** Earlier accuracy figures were self-authored: the stress generator and the extractor share an author, and the sample labels are the developer's. Here the ground truth (vendor, number, dates, items, amounts) is chosen by this repo's code, but the *rendering* (layout, wording, typos, noise) was written by Grok, which has never seen the extractor's regexes; each rendering was checked to contain every fact. It is LLM-authored, not a set of real vendor invoices: a different author, not a different world.

* **rules**: the regex reader alone, no model.
* **gated**: what the pipeline does: the regex reading is used unless it is in doubt; then Grok reads it and the two are cross-checked.
* **always**: Grok reads every document (cross-checked): the ceiling, and what it costs.

*Critical* fields are the ones money depends on: vendor, invoice number, total, and each item's name and quantity. **Silent wrong** = a critical field is wrong *and* the approval policy would still approve the invoice (money would move). A wrong reading that triggers an unknown-item, arithmetic or vendor error is caught downstream: a rejection (perhaps a false one), never a wrong payment. *Flagged although right* counts correct readings that were still held for a person (a conflict between the two readers, or a warning).

## Reading this

* **Rules alone** read 28 of 58 documents fully right on the critical fields and would have paid **0** wrongly read ones. They fully handle these layouts: bullets, caps, cells, columns. They need the model for: email, multiline, ocr, prose, refs, terse, thread, twocol. Where the rules fail they fail *safely*: the invoice is held, never paid wrongly, which is why the model is a cost and automation question here, not a safety one.
* **With the model, asked only when the rules are in doubt** (`gated`, the pipeline's behaviour): 58 of 58 fully right on the critical fields, 0 wrongly paid, 33 model calls. **Asked about every document** (`always`): 58 of 58, 0 wrongly paid, 58 calls. Gating gives the same accuracy for 57% of the calls.
* On the provided sample invoices the rules already read everything correctly, so the model has nothing to fix there; this corpus, written by a different author, is where it earns its keep. (The other place it changes outcomes is `data/self_correction/`, mistyped item names.)
* What made the model's answers usable, found by this evaluation: accepting a model value the regex missed when it appears in the document (instead of treating any difference as a conflict), cutting item descriptions down to product names, treating shipping/tax lines as charges not items, and keeping a vendor's own invoice-number scheme (`SI-1024` had been rewritten to `INV-1024`). Before those changes the same model reached 74% with 25 correct readings held for a person.
* Limits: LLM-authored documents, one model's idea of 'messy', not real vendor invoices; 58 documents is enough to see patterns, not to quote a precise error rate; the model runs are a single recording (re-record with `--record`). The date and tax fields are not critical and are checked less strictly: a date the regex reads confidently is not second-guessed.
